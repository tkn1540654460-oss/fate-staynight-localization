# 自动化汉化流水线

本文描述一套可以迁移到不同 PS Vita 游戏的工程流程。它不是“万能汉化器”：通用部分负责连接、安全、任务编排和校验；游戏相关部分由格式适配器完成。

## 1. 阶段与产物

| 阶段 | 输入 | 输出 | 必须通过的检查 |
|---|---|---|---|
| 发现 | VitaShell FTP | Title ID、目录和版本记录 | 只读访问 |
| 提取 | 自备游戏资源 | 原始/解密副本 | 哈希、大小、来源记录 |
| 解包 | 容器和脚本 | 可编辑中间文件 | 未修改往返测试 |
| 抽取 | 可编辑脚本 | UTF-8 JSONL | 稳定 ID、控制码显式化 |
| 翻译 | JSONL、术语表 | 批次检查点 | ID、占位符、控制码 |
| 合并 | 原记录、检查点 | 完整中文 JSONL | 无缺失、无冲突 |
| 字体 | 中文字符集、原字体 | 新字形与映射表 | 槽位唯一、全字符覆盖 |
| 注入 | 中文 JSONL、中间脚本 | 重建资源 | 可重新解包、结构一致 |
| 部署 | rePatch 树 | PSV 补丁 | 仅写 `ux0:/rePatch` |
| 回归 | 真机 | 验证记录 | 启动、显示、换行、存档 |

任何阶段失败都应停在当前阶段，不覆盖前一阶段产物。

## 2. 工作区约定

建议每个游戏独立建目录：

```text
projects/<game>/
├── project.json
├── original/
├── decrypted/
├── extracted/
│   ├── scripts/
│   ├── dialogue.jsonl
│   └── translation/batches/
├── translation/
│   ├── glossary.json
│   ├── prompt.md
│   └── schema.json
├── build/
└── repatch/
```

`project.json` 至少应记录 Title ID、区域/版本、引擎、原始文件相对路径和适配器版本。IP 地址、登录信息以及用户目录不属于项目元数据。

## 3. 文本记录格式

推荐一行一个 JSON 对象：

```json
{"id":"scene01:00042","script":"scene01","instruction_index":42,"page":3,"command":"TEXT","source_template":"少女は言った。@n","source_text":"少女は言った。","translation":null}
```

关键约束：

- `id` 在重新提取相同版本时必须稳定且唯一。
- `source_template` 保存可逆结构，未知字节写成显式 RAW 标记。
- `source_text` 只用于给译者/模型阅读，不用于注入定位。
- `translation` 最终必须重新包含需要的引擎控制码。
- 注入依据 ID 和指令位置，不能只用“查找相同日文”。

## 4. 控制码保护

模型不适合维护长而复杂的二进制标记。建议在每条记录内，把连续控制码替换成短占位符：

```text
输入模板：  {{RAW:8123}}彼女は走った。@n^
模型输入：  ⟦0⟧彼女は走った。⟦1⟧
模型输出：  ⟦0⟧她跑了起来。⟦1⟧
恢复结果：  {{RAW:8123}}她跑了起来。@n^
```

恢复前必须逐条验证：占位符的编号、数量和顺序完全相同。校验失败时只重试该条，不丢弃整批安全结果。

## 5. 批量翻译策略

实践中稳定且高吞吐的做法：

1. 给模型一段精简、固定的世界观和文风说明；
2. 只发送本批原文中实际出现的术语；
3. 只要求返回 `id` 和 `translation`；
4. 用 JSON Schema 约束根对象和字段；
5. 每批约 300–500 条，但同时设置字符上限；
6. 使用有限并发，避免瞬间耗尽账户或服务额度；
7. 每次成功结果原子写入独立检查点；
8. 配额耗尽时读取服务给出的重置时间，等待后原地续跑；
9. 最后单路扫描所有 ID，补齐并发分片可能留下的空洞。

翻译质量依赖上下文。记录应按剧情顺序发送；人物名、职阶、魔术术语和固定句式应进入版本化术语表。模型输出仍需人工抽查和真机回归。

## 6. 检查点与合并

每个检查点是 JSON 数组：

```json
[
  {"id": "scene01:00042", "translation": "她跑了起来。@n", "notes": ""}
]
```

合并器应做到：

- 忽略损坏或尚未写完的临时文件；
- 同一 ID 的相同结果允许重复；
- 同一 ID 的不同译文视为冲突并停止；
- 检查点中的未知 ID 视为错误；
- 缺一条都不生成“完整成品”；
- 按源 JSONL 顺序输出，而不是按文件名或完成时间排序。

## 7. 字体与编码

许多 Vita 游戏不是 UTF-8，脚本编码和字体槽位绑定。常用办法是在原编码中选择游戏未使用的字符槽，把其字形替换为目标汉字，并在注入时把目标汉字编码成对应槽位。

映射前必须计算：

- 全部译文的唯一字符集；
- 原脚本实际使用的编码槽位；
- UI、存档名、系统文本等非剧情文本所需槽位；
- 每套字体/字号中相同槽位的位置；
- 标点、全角/半角和换行宽度。

映射表必须一对一、可重复生成，并在所有字体档案中同步应用。不要占用仍被日文或系统界面使用的字符。

## 8. 格式适配器验收

一个可公开复用的游戏适配器至少要提供：

- `unpack`：资源 → 中间文件；
- `extract`：中间文件 → 稳定 ID JSONL；
- `inject`：中文 JSONL → 修改后的中间文件；
- `repack`：中间文件 → 资源；
- `verify`：结构、数量、控制码和往返检查；
- `layout`：可选的文本宽度/分页检查；
- `font`：可选的字符槽位与字形构建。

测试样本应是自己制作的最小二进制夹具，不能提交商业游戏资源。

## 9. 分阶段真机验证

建议顺序：

1. 不改内容，验证原资源解包和重建；
2. 替换一条现有字符范围内的文本；
3. 注入 2–3 个自定义中文字形；
4. 验证一个完整场景的控制码、换行和语音同步；
5. 验证一个章节以及存档/读档；
6. 构建全量补丁并做路线回归。

每次只向 `ux0:/rePatch/<TITLEID>/` 写入。若游戏无法启动，移走对应 rePatch 补丁即可回滚，不要改写 `ux0:/app`。

## 10. 发布前检查

- 仓库中没有游戏文件、脚本正文、完整译文、固件或密钥；
- 没有 `config.json`、IP、邮箱、OAuth 码、Token 或模型缓存；
- 第三方工具只以链接和安装说明引用，或许可证明确允许再分发；
- 测试夹具为自制数据；
- README 清楚说明支持范围和风险；
- 从全新克隆运行单元测试与打包检查。
